# 1. 技术栈

项目采用：

* React
* Vite
* JavaScript 或 TypeScript
* HTML5
* CSS3

项目为纯前端应用，不依赖后端服务器。

---

# 2. 架构原则

采用组件化、模块化设计。

需要尽量做到：

```text
UI
 ↓
业务逻辑
 ↓
数据层
```

分离。

不要将骰子计算、随机表处理、本地存储等核心逻辑全部直接写进 React 页面组件。

---

# 3. 建议模块

可以根据实际项目结构调整，但原则上至少区分：

```text
src/
├── components/
├── pages/
├── features/
├── services/
├── utils/
├── hooks/
├── data/
└── types/
```

其中：

### components

存放通用 UI 组件。

例如：

* Button
* Modal
* Table
* SearchBox
* Filter
* ResultPanel

### features

存放具体业务功能：

```text
features/
├── dice/
├── tables/
├── entries/
├── generators/
├── history/
└── storage/
```

### services

存放数据访问和业务服务。

例如：

* 本地数据服务
* 随机表服务
* 导入导出服务

### utils

放通用工具函数。

例如：

* Dice Parser
* Random
* Range Matcher
* Weight Random

---

# 4. 骰子引擎

骰子系统应作为独立模块。

需要能够：

```text
解析表达式
 ↓
生成骰子
 ↓
计算结果
 ↓
返回结构化结果
```

不要让页面组件自行处理骰子算法。

推荐返回类似：

```text
{
  expression,
  rolls,
  modifier,
  total
}
```

后续可以在不修改 UI 的情况下增加：

* 优势
* 劣势
* 保留高低
* 重掷
* 爆骰
* 成功判定

---

# 5. 随机表引擎

随机表逻辑应该独立。

至少处理：

```text
数值 → 范围 → 结果
```

以及：

```text
权重 → 随机 → 结果
```

业务逻辑不要直接依赖具体表格内容。

这样同一个引擎可以服务于：

* 事件
* NPC
* 地点
* 物品
* 怪物
* 任务

---

# 6. Generator 系统

随机生成器采用配置驱动思想。

生成器应能够描述：

```text
步骤
 ↓
使用哪个随机表
 ↓
如何获取结果
 ↓
是否依赖前面的结果
 ↓
如何组合最终文本
```

例如：

```text
Generator
 ├── Step 1: Weather
 ├── Step 2: Location
 ├── Step 3: Encounter
 ├── Step 4: NPC
 └── Step 5: Special
```

不要针对“NPC 生成器”“事件生成器”等分别开发完全独立的代码框架。

---

# 7. 数据驱动

随机表、词条和内置生成器应该使用独立数据文件。

例如：

```text
public/
└── data/
    ├── tables.json
    ├── entries.json
    └── generators.json
```

也可以根据实际需求进一步拆分。

React 组件不应大规模硬编码随机内容。

---

# 8. 内置数据与用户数据

需要明确区分：

```text
内置数据
+
用户数据
```

内置数据：

* 项目随代码发布
* 作为默认数据
* 不允许用户直接修改原始内容

用户数据：

* 用户自己创建
* 保存在浏览器
* 可以修改、删除、导入、导出

读取时可以形成：

```text
内置数据
+
用户数据
=
当前可用数据
```

---

# 9. 本地存储架构

本地存储是核心模块。

根据数据规模选择：

* localStorage
* IndexedDB

简单设置和少量配置可以使用 localStorage。

随机表、词条、历史记录和生成器等结构化数据较多时，优先考虑 IndexedDB。

本地存储模块应提供统一接口，例如：

```text
save()
load()
update()
delete()
clear()
export()
import()
```

UI 层不应直接到处调用：

```text
localStorage.setItem(...)
```

而应该统一通过数据服务处理。

---

# 10. 数据版本

用户数据需要有版本号。

例如：

```json
{
  "version": 1,
  "tables": [],
  "entries": [],
  "generators": [],
  "settings": []
}
```

未来修改数据结构时，可以根据版本进行迁移。

---

# 11. 导入与导出

导出内容应该能够保存用户数据。

推荐提供完整备份：

```text
用户随机表
用户词条
用户生成器
用户设置
收藏
```

导出格式优先采用 JSON。

导入时：

1. 校验文件格式
2. 检查数据版本
3. 检查必要字段
4. 必要时执行迁移
5. 写入本地存储

错误数据不能导致整个应用崩溃。

---

# 12. 状态管理

项目初期尽量不要为了状态管理引入过重的框架。

先根据实际复杂度判断：

* React state
* Context
* 自定义 hooks

如果后续跨页面共享状态明显增加，再考虑引入专门的状态管理库。

---

# 13. 路由

如果应用页面较多，可以使用 React Router。

例如：

```text
/
 /dice
 /tables
 /entries
 /generators
 /history
 /storage
 /settings
```

需要考虑 GitHub Pages 的静态部署环境。

---

# 14. 性能

项目以轻量为目标：

* 减少依赖
* 避免大型 UI 框架
* 避免不必要的运行时开销
* 数据按需加载
* 避免一次加载大量无关内容
* 搜索和筛选尽量在本地快速完成

不需要为了理论上的高性能而过早复杂化架构。

---

# 15. GitHub Pages 兼容

项目必须可以通过：

```text
npm run build
```

生成静态构建结果。

Vite 项目需要正确处理 GitHub Pages 的 `base` 路径。

如果仓库名为：

```text
trpg-tool
```

对应：

```text
https://USERNAME.github.io/trpg-tool/
```

则项目应正确配置：

```text
base: "/trpg-tool/"
```

如果最终使用自定义域名，再根据部署方式修改。

---

# 16. 开发原则

优先保证：

```text
功能正确
>
数据可靠
>
代码可扩展
>
界面美观
>
动画与特效
```

不要为了视觉效果引入不必要的复杂度。

所有核心业务模块都应该能够独立测试。
